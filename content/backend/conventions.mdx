## Tests structure

One folder per Django app inside `test_data/`. Each file inside is named after the URL resource segment. Mirrors the URL structure: `/api/<django_app>/<segment>/` → `test_data/<django_app>/<segment>.json`.

```
tests/
├── test_data/
│   ├── auth/
│   │   └── tokens.json
│   └── hr/
│       ├── employees.json
│       └── tasks.json
├── conftest.py         # Fixture setup and parametrize hook
└── test_api.py         # Single test function — parametrized over all cases
```

See [API Testing](/code/api_testing) for the full data-driven testing standard.

## Django app structure

```
api/
└── auth/
    ├── migrations/
    │   └── __init__.py
    ├── tests/
    │   ├── __init__.py
    │   ├── test_models.py
    │   ├── test_views.py
    │   ├── test_services.py
    │   └── test_serializers.py
    ├── __init__.py
    ├── admin.py
    ├── apps.py
    ├── models.py
    ├── views.py           # Request/response only — no business logic (can be a folder: views/__init__.py, views/auth.py, …)
    ├── urls.py
    ├── serializers.py     # DRF serializers — API input/output validation (can be a folder: serializers/__init__.py, serializers/auth.py, …)
    ├── schema.py          # Internal DTOs as @dataclass(slots=True); Pydantic only for untrusted external data
    ├── services.py        # Business logic, decoupled from views (can be a folder: services/__init__.py, services/auth.py, …)
    ├── types.py           # Type aliases, Literal, TypedDict, Enum
    ├── permissions.py     # DRF custom permission classes — always a root-level file.
    ├── exceptions.py      # Custom exception classes
    └── utils.py           # App-scoped helper functions
```

## Comments

Only add comments where the complexity warrants it — not by default.

| Level | When to add |
| --- | --- |
| Module | Non-obvious purpose or constraints that aren't clear from the filename |
| Class | Complex invariants, ownership rules, or non-obvious design decisions |
