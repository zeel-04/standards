# Sticky elements

Sticky elements stay in view while the rest of the screen scrolls. Use them only when something must always be visible — not by default.

## Principle

Most UI should scroll. Pin it only if losing it forces the user to scroll back:

- **Reachability** — they need to act without scrolling to find the control. 
  
  > Example: *A long settings form: the user edits fields halfway down and needs Save/Cancel without scrolling back to the top.*
- **Context** — they need to track where they are while reading. 

  > Example: *A data table: column headers must stay visible so the user knows which column they're in while scrolling through hundreds of rows.*

If neither applies, don't pin it. Length alone never justifies stickiness. Sticky elements add visual weight and shrink the scrollable area, so keep them short enough not to crowd the scroll area on small viewports.

## Anatomy

Every sticky layout is the same three-row structure: a pinned top, a scrolling middle, a pinned bottom. Either pinned row is optional; the middle is always the one that scrolls.

`position: sticky` fails silently inside a parent that has `overflow: hidden` and no defined height. Give the scroll container an explicit height.

## Sticky action bars

The most common use of stickiness: an edit, settings, or form screen where the user must always be able to reach **Save** and **Cancel** without scrolling. Title sits in the top bar; commit actions sit in the bottom bar (desktop) or top bar (mobile, short forms).

When a screen enters edit mode with Cancel and Save, hide tab bars and floating action buttons. A Create FAB and a Cancel/Save pair are different mental models and must not share a screen.

### Desktop

Title left, optional contextual actions right. Commit actions live in a sticky footer, right-aligned, with a single primary action last. Disable Save until the form is modified.

### Mobile

Mobile has two distinct conventions for sticky actions. Pick deliberately — they're not interchangeable.

#### Pattern A — top-bar Save (short edits)

Back, title, Cancel, and Save all sit in the sticky top bar. The body fills the rest of the screen. Matches the iOS Mail / Contacts / Settings convention.

<Preview>
  <StickyActionBarMobileTopDemo />
</Preview>

Use when:

- The form is short (fits within ~1–2 screens).
- Save is reversible and low-stakes (edit profile, rename a thing).
- The screen is presented as a modal sheet over a list.

Acceptable for an action the user taps once per visit, painful for anything frequent (see thumb reach below).

#### Pattern B — sticky footer CTA (commit / pay / submit)

The primary action becomes a full-width button in a sticky footer, padded clear of the home indicator. Reserve this for weighty actions where the label should carry value ("Place order · $1,983.60", "Save changes").

<Preview>
  <StickyActionBarMobileFooterDemo />
</Preview>

Use when:

- The action is irreversible, costly, or the screen's whole purpose (checkout, payment, publish).
- The form is long enough that scrolling is expected.
- You want the CTA to dominate — full-width signals weight.

### Mobile-specific gotchas

- **Thumb reach.** Top-right Save is the worst zone on a phone. Don't put a frequently-tapped action there.
- **Keyboard behavior.** When the on-screen keyboard opens, the sticky footer must either stay above it or recede with the layout — never let the keyboard cover the Save button. Test this; it's the most common sticky-bar bug on mobile.

## Sticky table headers

Data tables with many rows need column headers to stay visible as the user scrolls. Combine a sticky `<thead>` with a fixed-height scrollable body, then place pagination **below** the scroll container — it belongs to the table as a whole, not to the visible body.

<Preview className="px-0 py-8 items-start">
  <StickyTableDemo />
</Preview>

- Set a **fixed height** on the scroll wrapper so the table doesn't grow to fit all rows.
- Apply `sticky top-0` to `<thead>` and match its background to the page so row content doesn't bleed through on scroll.
- Place pagination outside the scroll container — users need it reachable without scrolling the rows.
